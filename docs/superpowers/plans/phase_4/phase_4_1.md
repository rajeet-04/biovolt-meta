# Phase 4.1: Shared Command and Acknowledgement Contracts Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Define versioned server-to-device command and device-to-server acknowledgement contracts that can be validated identically by backend tests, simulator tests, and ESP32 serializer/parser tests.

**Architecture:** Commands and acknowledgements are new message types carried on the existing authenticated `/ws/device` WebSocket. JSON Schema remains the cross-language source of truth. Command payloads use a discriminated `kind` field with a small fixed command set, finite expiry, and explicit `command_id` correlation.

**Tech Stack:** JSON Schema Draft 2020-12, existing shared contract test harness, Python jsonschema, canonical JSON examples.

**Spec:** `docs/architecture/software-architecture.md`

## Global Constraints

- Do not modify `device-telemetry.v1` field meaning.
- `command_id` is UUID text generated by FastAPI.
- `issued_at` and `expires_at` are server UTC timestamps.
- Device does not need a synchronized RTC to enforce expiry; backend must not send already-expired commands, and the device rejects commands whose optional `ttl_ms` has elapsed relative to receipt/uptime.
- Every acknowledgement references exactly one `command_id`.
- Acknowledgement status enum is `accepted`, `applied`, `rejected`, `failed`.
- `applied` may include actual device actuator/control state after safety clamping.
- No arbitrary shell, GPIO-number, raw-I2C, or free-form executable command exists.

### Task 3: Document command lifecycle and idempotency

**Files:**
- Create: `docs/protocols/device-command-protocol.md`
- Modify: `docs/architecture/software-architecture.md`

Document exact lifecycle:

```text
FastAPI creates command
  -> queued
  -> sent on authenticated /ws/device
  -> ESP32 validates
  -> optional accepted ack
  -> ESP32 safety-gates and applies
  -> applied/rejected/failed ack
  -> FastAPI records terminal state
```

Duplicate rule:

```text
same command_id received again
  -> do not repeat actuator effect
  -> return cached terminal acknowledgement when available
```

Expiry rule:

```text
backend current time >= expires_at
  -> do not send
  -> mark expired
```

Device-side TTL rule:

```text
receipt uptime + ttl_ms exceeded before application
  -> reject expired
```
